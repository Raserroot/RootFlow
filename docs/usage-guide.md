# RootFlow 使用教程

> 面向使用者的操作手册。**所有路径、按钮文案、环境变量名都以当前实现为准**
> （与 `REQUIREMENTS.md` 的早期设计与 `docs/` 里的规格可能有差异，本文以实装为准）。
> 适用版本：**1.0.0**（`versionCode 2`）。

---

## 0. 它是什么

RootFlow 是一个 **Root 脚本宿主**。它自己**不含**任何自动化规则，只做四件事：

```
监听系统事件  →  投给常驻脚本  →  把脚本输出实时打屏  →  出事时熔断保命
```

所以你的工作只有两件：**写脚本**，以及决定它**什么时候跑**：

- **要响应系统事件**（开机、亮屏、定时…）⇒ 运行方式选 **「常驻」**，再勾上关心的事件，
  脚本里用 FIFO 读事件（§3）
- **只想跑一遍** ⇒ 选「单次」：它不会被事件唤起，也不会常驻
- 整块的闸门是主页最上面的 **总开关**（§5.1）：关掉它，任何脚本都不会启动

## 1. 首次上手（5 分钟）

### 1.1 准备

- 一台**已 Root** 的手机（本项目在 OnePlus 8 / Android 15 / APatch 上开发与验证）
- 授予 RootFlow **root 权限**（首次运行时 Root 管理器会弹窗，选"允许"并记住）

### 1.2 三个权限，请都授予

打开 App → **设置** Tab → **关于** → 「权限总览」逐项检查。其中三项**必须**：

| 权限 | 为什么必须 | 不授予的后果 |
|---|---|---|
| **通知** | 前台服务靠通知常驻 | 服务被系统随时清理，事件丢失 |
| **使用情况访问**（PACKAGE_USAGE_STATS） | 「前台应用 / 退到后台」两个事件靠它 | 这两个事件不可用（其余 11 个照常） |
| **电池优化白名单** | 防止系统冻结后台 | 熄屏久了服务被杀，事件不再触发 |

「关于」页里每项都有 **去设置** 按钮，点它直接跳到对应的系统页面。

> 「精确闹钟」（SCHEDULE_EXACT_ALARM）**不是必须**：v1 的「定时」事件默认走**非精确**路径，
> 未授权也能用，只是触发时刻可能有分钟级误差。

### 1.3 确认服务在跑

打开 App 后**主页**第一张卡应显示 **「服务运行中」**（淡紫色底）。

> ⚠️ **重要**：RootFlow 的前台服务**不是开机自启**——它由**本 App 被打开时**拉起。
> 手机重启后，**你需要手动打开一次 RootFlow**，服务才会恢复、事件才会重新监听。
> 这是有意为之（Android 12+ 限制后台启动前台服务），不是缺陷。

## 2. 写第一个脚本

### 2.1 创建

1. **配置** Tab → 右下角 **+** 按钮
2. 填写：
   - **名称**：随便起，例如 `开机打个招呼`
   - **语言**：`shell`（v1 只支持 shell；Lua 仅是接口预留）
   - **启用**：打开
   - **超时（秒）**：`0` 表示用默认 60 秒，或填具体秒数
   - **脚本正文**：写 shell 代码（见下）
3. 点右下角 **✓**（保存）

### 2.2 脚本正文长什么样

就是**普通的 `/system/bin/sh` 脚本**，以 **root 身份**执行，工作目录是**该脚本自己的目录**。

```sh
#!/system/bin/sh
# 启动那一刻注入的环境变量（见 §3.3）
echo "事件: $ROOTFLOW_EVENT"
echo "脚本 id: $ROOTFLOW_SCRIPT_ID"
echo "宿主版本: $ROOTFLOW_APP_VERSION"
echo "安全模式: $ROOTFLOW_SAFEMODE"
# 没有负载时 ROOTFLOW_EVENT_PAYLOAD 这个变量根本不存在，所以要判断
[ -n "$ROOTFLOW_EVENT_PAYLOAD" ] && echo "负载: $ROOTFLOW_EVENT_PAYLOAD"

# 你的实际动作，例如：
# settings put system screen_brightness 120
# cmd wifi set-wifi-enabled disabled
echo "干完了"
```

> **上面这个是「单次」脚本的样子**：跑一遍、打印、结束。
> 想让它**一直在**、并且**接收后续事件**（亮屏、WiFi 变化…），就要把运行方式改成
> **「常驻」**，正文写成循环 + 读 FIFO —— 那才是本项目的常见形态，见 §3.1 的例子。

**要点**

- **不需要写 `su`**——脚本本身就是 root 身份在跑
- **正文不要包含 `exit`**：脚本被包在 subshell 里，但 `exit` 仍会打断收尾步骤（退出码与 stderr 回收）
- 想输出错误、又想让它显示成红色？直接写 **stderr** 即可（`echo "出错了" >&2`）
- 长跑脚本请注意「超时」设置：超时会触发熔断（见 §6）

### 2.3 保存后文件在哪（想手改的话）

| 内容 | 位置 |
|---|---|
| 脚本正文 | `/data/local/tmp/rootflow/scripts/<脚本id>/main.sh` |
| 脚本元数据 | Room 数据库（不在文件系统） |
| 安全模式标记 | `/data/local/tmp/rootflow/safemode.flag` |

> ⚠️ **不要直接改正文文件**。正文有两处真相（文件 + 数据库里的**内容摘要**），
> App 在打开编辑器时会**校验摘要**：手改过文件之后，编辑器会**直接拒绝打开**，
> 并提示「正文与记录摘要不符（文件被外部改动）」（2026-09-24 真机实测）。
> **正确做法**是在 App 的编辑器里改正文并保存。同理，**不要在手机端直接改数据库**。

## 3. 事件通知：把系统事件投给你的常驻脚本

> **★ 先读这一条（总开关重构后最重要的语义变化）**
> 事件**不再是"启动脚本的理由"**。它现在是一条**通知**：事件发生时，宿主把它**投递**给
> **正在常驻运行**的那个脚本，由脚本自己决定要不要理它。
> ⇒ **单次脚本收不到任何事件**（它只在服务启动时跑一遍）。
> 想做"开机时做点什么"，就把脚本设成**常驻** + 勾「开机」，再在脚本里读事件（读法见 §3.1）。

**在哪勾**：**配置** → 点脚本进**编辑器** → 拉到底部 **「事件通知（高级，可选）」**
（默认折叠，点标题展开）→ **点 chip 即勾选**（改动**立即保存**，不需要点保存按钮）。

| Chip | 事件键 | 什么时候投递 | 需要的参数 |
|---|---|---|---|
| **开机** | `boot` | 开机完成 | — |
| **亮屏** | `screen_on` | 屏幕点亮 | — |
| **熄屏** | `screen_off` | 屏幕熄灭 | — |
| **解锁** | `unlock` | 解锁成功 | — |
| **前台应用** | `app_foreground` | 切到某个 App 前台 | 可选：包名（留空 = 任意 App） |
| **退到后台** | `app_background` | 某 App 退到后台 | 可选：包名 |
| **定时** | `time` | 每天固定时刻 | 小时 + 分钟 |
| **间隔** | `interval` | 每 N 分钟一次 | 间隔分钟数 |
| **低电量** | `battery_low` | 电量低 | — |
| **电量恢复** | `battery_okay` | 电量恢复正常 | — |
| **接电源** | `power_connected` | 插上充电器 | — |
| **断电源** | `power_disconnected` | 拔掉充电器 | — |
| **WiFi 变化** | `wifi_changed` | Wi-Fi 连接状态变化 | — |

**参数在哪填**：勾了带参数的 chip 后，下方会出现对应输入框（例如「定时」出现小时/分钟，
「间隔」出现分钟数，「前台应用」出现包名）。另外**所有事件**都有一个
**「事件负载（ROOTFLOW_EVENT_PAYLOAD）」** 框，可填任意字符串。

**投递的两个前置条件**（缺一个就投不出去）：

1. **总开关开着**（见 §5.1）—— 关着时事件源会**全部停止**，事件根本不会产生；
   同时"没有任何生效订阅"的事件源本身也不会启动（按需启，省电）
2. **那个脚本此刻真的在跑**（常驻 + 已启用 + 没被安全模式挡住）—— 没在跑就记一条
   `EVENT_NOT_RUNNING` 日志然后**丢弃**：事件**不排队、不补发**

> **勾了事件 ≠ 脚本会因此启动。** 这是刻意的：事件是"通知"，不是"开关"。
> 想让它一直在，就把运行方式选 **「常驻」**；只想跑一次，就手动运行。
>
> 「事件负载」框填的内容会随**每次投递**一起送出去（格式见 §3.1）；
> 而 `$ROOTFLOW_EVENT_PAYLOAD` 那个**环境变量**只反映**脚本启动那一刻**的事件（见 §3.3）。

### 3.1 脚本怎么收到事件（FIFO 通道）

事件**不是**用环境变量传的 —— 环境变量在脚本**启动那一刻**就固定了，而事件是**随时**来的。
宿主给每个运行中的脚本开一条 **FIFO**（命名管道），路径在环境变量 `ROOTFLOW_EVENT_FIFO` 里：

```sh
#!/system/bin/sh
while true; do
  if read -r ev < "$ROOTFLOW_EVENT_FIFO"; then
    echo "收到事件：$ev"        # 形如  boot   或   wifi_changed 家里WiFi
  fi
done
```

- 每一行是 **`事件键`**，或 **`事件键 负载`**（空格分隔；负载就是你在编辑器「事件负载」框里填的）
- 写端**只在事件投递期间**才打开 ⇒ `read` 是**阻塞等待**，不占 CPU、不用轮询
- 脚本没在跑时事件**不缓存**：投不出去就记一条 `EVENT_NOT_RUNNING` 然后丢掉
- 通道开不出来时（root 通道异常），宿主**不会**注入这个变量，并记下
  `(no ROOTFLOW_EVENT_FIFO; the script will not receive later events)` ——
  变量**缺席**就是"没有通道"，不是"路径是空的"

> ⚠️ **这一节的读法在真机上尚未逐条验证过**。宿主侧的投递路径已验证
> （`EVENT_DELIVERED` / `EVENT_NOT_RUNNING` / `EVENT_NO_READER` 都有真机日志），
> 但"脚本真的 `read` 到了"这一步还没在设备上跑通。若你试了读不到，请把日志里的
> `EVENT_*` 行发出来。

### 3.2 运行方式：单次 / 常驻

编辑器里的 **「运行方式」** 是二选一 —— 它决定了脚本**会不会收到事件**：

| | **单次** | **常驻** |
|---|---|---|
| 什么时候跑 | 服务启动时跑**一遍**就结束（也可手动运行） | 服务一起来就跑，**退出/被杀自动拉起** |
| **收事件** | **不收** | **收**（见 §3.1） |
| 超时 | 默认 60s（可改） | **不限时**（不会因跑太久被当超时杀掉） |
| 退出后 | 结束 | 自动重新拉起，退避 **1s → 2s → 4s → 8s**（封顶 30s） |
| 崩溃太多 | 走 §6 的全局熔断 | 连续快速崩（每次活不到 5 秒）**5 次**后**只停掉它自己** |
| 适用 | 一次性任务、开机初始化 | 守护进程、常驻监听、任何要收事件的脚本 |

> 「只停掉它自己」是刻意的：常驻脚本会反复重启，若照搬"连续失败 3 次进安全模式"
> 那条全局规则，一个写错的常驻脚本会把整个 App 冻住。

**常驻脚本的已知限制（不是 bug，是当前的设计边界）**

1. **改动脚本正文不会自动生效** —— 要让常驻脚本用上新正文，把「运行方式」切换一次，
   或重启 App。
2. **受总开关与安全模式双重约束**：总开关关闭时它**不会启动**，已经在跑的会被**终止**
   （总开关的语义见 §5.1）；熔断后同样不会跑。
3. **占一个并发名额**：全局上限 4 ⇒ 最多 4 个常驻脚本；超出的会被拒绝并记日志。

**怎么确认它在跑**：看 logcat 里的 `DAEMON_*` 行，例如

```
DAEMON_SUPERVISION_ADDED script=7 reason=trigger created or enabled
DAEMON_STARTED script=7 rapidCrashes=0
DAEMON_EXITED script=7 runMillis=... stable=...
DAEMON_RESTART_IN script=7 delayMillis=1000
DAEMON_GIVEN_UP script=7 reason=rapid crashes 5/5 (only this script stops; ...)
```

> ✓ **已修（2026-09-24）**：存活时长过去靠**轮询注册表**测量 —— `echo` 这类短命脚本
> 可能在两次轮询之间就跑完了、**一次都没被看见**，于是被记成 `0ms` 并判"快速崩"，
> 多罚退避、连崩 5 次后被停掉。现在时长由运行登记表在"开始 / 结束"两个时刻**直接记下**，
> 与轮询无关；万一是"没被看见就跑完"的那种，日志会给出
> `DAEMON_APPEAR_MISSED … measuredMillis=…`，数值同样是真实的。

### 3.3 注入给脚本的环境变量（全集）

| 变量 | 内容 | 备注 |
|---|---|---|
| `ROOTFLOW_SCRIPT_ID` | 脚本主键（数字） | |
| `ROOTFLOW_EVENT` | **启动那一刻**的事件键（如 `boot`） | 手动运行时为**未定义**；运行期的事件走 §3.1 的 FIFO |
| `ROOTFLOW_EVENT_PAYLOAD` | **启动那一刻**的事件负载 | **无负载时该变量不存在**（不是空串） |
| `ROOTFLOW_EVENT_FIFO` | 事件通道的**路径**（用法见 §3.1） | **有通道才存在**：缺席 = 宿主开不出 FIFO，之后的事件都收不到 |
| `ROOTFLOW_APP_VERSION` | 宿主版本（如 `1.0.0`） | |
| `ROOTFLOW_SAFEMODE` | `"true"` / `"false"` | **始终存在** |

> 注意变量名是 `ROOTFLOW_EVENT`（**不是** `ROOTFLOW_EVENT_ID`）。
> 也**别**把 `ROOTFLOW_EVENT` / `ROOTFLOW_EVENT_PAYLOAD` 当成"最新事件"——
> 它们冻结在启动那一刻；**运行期的事件请读 FIFO**。

## 4. 看日志

**主页** → 最下面的 **「运行日志」** 卡片：

- **过滤 chip**：`全部` / `OUT`（标准输出，白） / `ERR`（标准错误，红） / `SYS`（宿主消息，灰）
- **自动跟随**：列表会跟着最新输出走；你手动往上翻它就**自动停止跟随**，滚回底部会**自动恢复**
- 右上角显示当前运行短码与行数；「暂无运行」表示还没跑过
- 单次运行的行数上限由管道环形缓冲决定，超出会显示**丢弃计数**（不静默丢）

**当前正在跑什么**：主页「服务状态」卡 + 「事件源」行给出概览。

## 5. 主页读什么

| 卡片 | 内容 |
|---|---|
| **总开关**（最上面） | 已打开 / 已关闭；下面两行是 `已启用 N 个脚本 · 常驻 M 个` 与 `服务运行中 · 事件源 X/7`；见 §5.1 |
| **服务状态** | 服务在不在跑；右侧图标：✓ 运行中 / ⚠ 安全模式 / ▶ 未运行 |
| **信息卡** | Android 版本 / 设备 / Root 方案 / SELinux / App 版本 / **事件源 N / 7 可用** |
| **运行日志** | 见 §4 |

### 5.1 总开关（★ 本轮重构的核心）

**它是全局闸门：关着的时候，任何脚本都不会启动。**

| 状态 | 含义 |
|---|---|
| **已打开** | 该跑的会跑：**常驻脚本**启动；有生效订阅的**事件源**跟着起来 |
| **已关闭** | **什么都不启动**；已经在跑的常驻脚本会被**终止**；事件源全部停掉 |

**它不会做的事**（这几条是不变量，不是"当前实现"）：

- **不动你的数据**：关闭它**不会**把脚本的「启用」关掉，也**不会**清空你勾的事件 ——
  它只是"现在不跑"，配置原样保留（卡片上那句"可随时修改"就是这个意思）
- **不停服务**：前台服务继续跑（它承载界面与保活），只是不再启动任何脚本

**「事件源 X/7」到底在数什么**：7 个事件源里**此刻真的在跑**的几个。两个影响因素：

1. **总开关关着** ⇒ 只剩 `power` / `battery` 两个。它们由系统按清单实例化，
   应用**无法在运行期停掉** ⇒ 关闸时如实显示 `2/7`，而不是假装 `0/7`
2. **总开关开着** ⇒ 只有"**你的某个脚本勾了它产出的某个事件**"的源才会启动（按需启，省电）

> 所以「总开关已关闭 + 事件源 2/7」是**正常**状态；打开开关、勾上事件后它会往上走。

**「它为什么没跑？」**：脚本列表里那颗 ⓘ 会列出整条判定链 ——
安全模式 / **总开关** / 脚本开关 / 崩溃重试 / 前台服务 / 运行方式，
第一处不通过的就是原因。**先看总开关那一条**：它是最常见的"什么都没动静"的答案。

> 「Root 方案」显示 `unknown` 是**正常**的：某些 Root 方案（如 APatch）没有可从系统读取的
> 稳定标记，宿主**不会猜**——它宁可如实说未知，也不编一个可能错的方案名。
> 旁边的 **SELinux** 一行可以帮你人工判断（例如 `u:r:magisk:s0`）。

## 6. 安全模式（熔断）—— 保命机制

### 6.1 什么时候会触发

| 触发条件 | 阈值 |
|---|---|
| 脚本运行超时 | 按脚本的「超时」设置，默认 60 秒 |
| 同一脚本连续失败 | ≥ 3 次 |
| 全局失败风暴 | 10 分钟内累计失败 ≥ 20 次 |
| Root 无响应 | `su` 命令超过 10 秒没返回 |
| 高频自启 | 同一脚本 60 秒内被触发 ≥ 20 次 |
| 连续异常启动 | 60 秒内连续崩溃 3 次（bootloop 兜底） |
| **手动** | 你自己点「立即熔断」 |

### 6.2 触发后会怎样

1. 写入 `/data/local/tmp/rootflow/safemode.flag`
2. 杀掉所有正在跑的脚本（整个进程组）
3. **拦下后续事件**（内存级闸门）—— 注意**它不会改动你的任何配置**：
   脚本的「启用」、运行方式、勾的事件**全部原样保留**
4. 前台服务进入安全模式
5. 发高优先级通知
6. 写 `logs/safemode.log`

此后**不会再启动任何脚本，事件也不再投递**——除了一种例外：开启「**安全模式下仍运行**」的脚本仍会被显式执行。

> 为什么第 3 步改成"内存闸门"而不是"去数据库里把触发器禁用"：熔断是**故障路径**，
> 此刻做越多 IO 越可能自己失败；而且**改用户数据**会留下"恢复后配置仍被打坏"的形态。
> 现在熔断**完全不动用户数据**。

### 6.3 怎么退出

- **App 内**：**设置** → **安全熔断** → 「退出安全模式」
- **通知**：点安全模式通知进入恢复入口
- **手动兜底**（App 打不开时）：
  ```
  su -c "rm -f /data/local/tmp/rootflow/safemode.flag"
  ```
  然后重启 App 即可。**没有需要"还原"的东西** —— 熔断从未改动你的脚本与订阅。
  （设置页那两个恢复选项现在**运行时行为相同**；第二个只是把"保持停止"的意图记进日志。）

### 6.4 主页的红色横幅

主页顶部出现红条「已进入安全模式 · 脚本已全部停止」即表示处于熔断态；
下方会写明**成因**。若成因无法还原，它会**如实说"未知"**，而不是编一个原因。

## 8. 必须知道的三条设备/设计事实

### 8.1 服务不是开机自启

手机重启后要**手动打开一次 RootFlow**（见 §1.3）。也正因如此，「开机」事件实际上
是**你打开 App 时**补发的——某些系统（如 ColorOS）会在分发阶段拦截系统开机广播，
宿主用"App 启动时补发"来绕过它。

> 所以：**想开机跑脚本，就得开机后打开一次 App。** 这是当前实现的天花板，不是配置问题。
>
> ⚠️ **另一个已知缺陷（当前版本请避开）**：打开 App 之后，那条补发的 `boot` 事件
> **很可能在常驻脚本跑起来之前就发出去了** —— 事件投不出去就丢弃（见 §3 的前置条件 2）。
>
> **请这样做**：如果你的脚本开机后要一直运行，直接选 **「常驻」** ——
> 它**不需要 boot 事件也会启动**（服务一起来就跑），把初始化写在脚本开头即可，
> 不必依赖 `boot`。这个时序问题已登记在 `PROJECT_STATE.md`。

### 8.2 别用工具改数据库 / 反向写回文件

- 数据库与正文文件是**两处真相**，从 PC 侧写回会绕过一致性检查
- **手改正文文件会让脚本在 App 里打不开**：编辑器会校验内容摘要，不符时直接报
  「正文与记录摘要不符（文件被外部改动）」（2026-09-24 真机实测）。
  要改正文，**在 App 的编辑器里改**。
- 同理，手机端直接改数据库也会让界面与库不一致

### 8.3 安全模式可能被"快速连开"误判

60 秒内连续启动 3 次会被 bootloop 兜底当成异常。**调试时不要连续快速重启 App**，
若真被误判，按 §6.3 清除 flag 即可。

## 9. 常见问题

**Q：什么脚本都不跑，是不是坏了？**
A：先看主页最上面的**总开关**（§5.1）—— 关着的时候任何脚本都不会启动，那正是它的本意。
总开关是开着的话，看脚本列表里那颗 **ⓘ**：它会列出 安全模式 / 总开关 / 脚本开关 /
崩溃重试 / 前台服务 / 运行方式 里**第一个没通过**的，原因直接写在那里。

**Q：我勾了事件（比如「亮屏」），脚本却没有反应。**
A：两个最常见的答案：① 「运行方式」是**单次** —— 单次脚本**收不到任何事件**（§3）；
② 脚本当时没在跑 —— 事件投不出去就**丢弃、不排队**。两者都还要先满足**总开关是开的**。

**Q：勾了「开机」，但重启后没跑。**
A：见 §8.1——重启后需手动打开一次 App。再确认三件事：总开关是开的、
脚本「启用」是开着的、**运行方式选的是「常驻」**（单次不会被事件唤起）。
若它一直失败，连续失败 3 次会**触发全局熔断**（进安全模式，见 §6），
届时所有脚本都停，需要按 §6.3 恢复。

**Q：「前台应用」勾了但没反应。**
A：检查「使用情况访问」权限（设置 → 关于 → 权限总览），并用「前台应用」那一行后面的
**去授权**按钮跳转授权。

**Q：脚本跑了但终端里没输出。**
A：① 看是不是被过滤了——切到 `全部` 或 `OUT`；② 输出经过了环形缓冲，**超长输出会被丢弃并显示丢弃计数**；
③ 脚本若把内容写到了 stderr，切到 `ERR` 才看得到。

**Q：脚本显示"失败"，但我手动跑是好的。**
A：脚本以 **root + 该脚本自己的目录**为工作目录运行，且**只注入了 §3.3 那 6 个变量**。
不要依赖登录 shell 的 `PATH` / `HOME` 等环境；用**绝对路径**调用命令。

**Q：怎么让某个脚本在安全模式下也能跑？**
A：编辑器里打开「**安全模式下仍运行**」。
（注意：总开关关着时这一项也不管用 —— 总开关的优先级在最上面，见 §5.1。）

**Q：编辑器里的「连续失败自动禁用」开关去哪了？**
A：**已移除**（2026-09-24）。它过去只是"摆在那里但不生效"；评估之后发现
**实现它同样没有意义**：需求给它的阈值（连续失败 ≥ 3）与熔断的
"同一脚本连续失败 ≥ 3 次"**完全相同** ⇒ 全局熔断（停所有脚本 + 进安全模式）
**必然抢先触发** ⇒ 那段代码永远不会被执行。
要让它有意义，得先改需求（阈值小于熔断，或者改熔断规则）。
底层字段仍然保留（旧数据不丢），只是不再有入口 —— 所以你**看不到它也不会丢配置**。
**现状下的正确做法**：某脚本反复失败时，手动把它的「启用」关掉。

**Q：怎么清掉某个脚本留下的东西？**
A：「设置 → 关于 → 卸载残留 → 清理残留」。它只删**确认是孤儿**的目录与事件订阅行，
非本项目写入的条目一律不动。

## 10. 一页速查

```
创建脚本    配置 Tab → +  →  写正文  →  ✓ 保存
选运行方式  编辑器 → 运行方式 → 单次 / 常驻（要收事件必须选"常驻"）
勾事件      编辑器 → 展开「事件通知（高级，可选）」→ 点 chip（立即生效）
读事件      while true; do read -r ev < "$ROOTFLOW_EVENT_FIFO"; done
开总开关    主页 → 总开关卡（关着 = 任何脚本都不启动）
看日志      主页 → 运行日志 → 全部/OUT/ERR/SYS
查权限      设置 → 关于 → 权限总览
看服务      主页 → 服务状态卡（✓ 运行中 / ⚠ 安全模式 / ▶ 未运行）
为什么没跑  配置 Tab → 脚本行里的 ⓘ（列出整条判定链）
熔断        设置 → 安全熔断 → 立即熔断
恢复        设置 → 安全熔断 → 退出安全模式
手动清 flag su -c "rm -f /data/local/tmp/rootflow/safemode.flag"
正文位置    /data/local/tmp/rootflow/scripts/<id>/main.sh
```

**六条最容易踩的**

1. **勾了事件但脚本没反应** ⇒ 先看「运行方式」是不是**常驻**（单次收不到任何事件，§3），
   再看主页**总开关**是不是关着（§5.1）
2. 服务**不是开机自启**——每次重启后手动开一次 App
3. 正文里**不要写 `exit`**
4. **启动那一刻**注入的变量叫 `ROOTFLOW_EVENT`（不是 `_EVENT_ID`）；无负载时
   `ROOTFLOW_EVENT_PAYLOAD` **不存在**。**运行期的事件不在这里** —— 要读 FIFO（§3.1）
5. 用**绝对路径**调命令，别指望登录 shell 的环境
6. 调试时**别连续快速重启 App**（会被误判成 bootloop 而熔断）

**常驻脚本专属三条**

1. 选「常驻」后**立刻生效**，不用等下次服务启动；切回「单次」会**终止已在跑的进程**
2. **改了正文不会自动生效** —— 把「运行方式」切换一次（或重启 App）
3. 它**不限时**、连崩 5 次**只停它自己、不会熔断整个 App**

- ~~「连续失败自动禁用」不生效~~ ⇒ **该开关已移除**（实现它永不可达，见 §9）
- ~~`runMillis` 量不准~~ ⇒ **已修**（时长改由运行登记表的两个真实时刻决定，见 §3.2）
- **脚本侧 FIFO 读法尚未在真机上验证**（§3.1）；宿主侧的投递路径是验证过的
- **`boot` 事件可能投不出去**：宿主会给它一个 6 秒重试窗口，但若你的脚本在那之后才跑起来，
  这次 `boot` 就丢了。**别依赖 `boot`** —— 要开机常驻就直接选「常驻」，
  把初始化写在脚本开头（见 §8.1）
